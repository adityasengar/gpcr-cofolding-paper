## Scramble procedure (decoy arm)

For each receptor, the cognate Gα α5-CT (last 11 residues) is 
permuted with a per-receptor seed derived from 
`SHA-256(receptor_slug + '|block_b_decoy_v1|' + variant)`. The variant starts at 0 
and increments if the first draw has Hamming distance < 5 from the 
original (rare — 11-char permutations of a diverse α5-CT composition almost always 
clear the floor on variant=0). If no draw clears the floor within 
64 tries, the script raises.

Composition is preserved by construction (a permutation cannot change amino acid 
counts). We assert `Counter(scrambled) == Counter(original)` per receptor as a 
defensive check; all 40 pass.

The rest of the Gα scaffold (α5 helix N-terminal to the CT, all other helices) is 
left byte-identical to the cognate Gα. The β and γ subunits are outside the scope 
of the single-partner-chain pipeline this feeds (Block A only used Gα-alone partners; 
β/γ are not part of the input FASTA schema in Block A).

## File count and dispatch integration

- **Per-receptor per-arm partner FASTAs**: 40 × 2 = **80 unique files** under 
  `refs/constructs_block_b/`.
- **Build manifest**: one row per (receptor, arm, backbone) — 40 × 2 × 4 = 
  **320 rows** in `refs/constructs_block_b/build_manifest.csv`.
- **Why 80 not 320 FASTAs**: the partner-sequence FASTA is upstream of the 
  per-backbone (yaml / json / fasta) input wrapper. `scorer/propose.py::
  materialise_inputs` wraps the same partner sequence into Boltz YAML, OF3 
  JSON, Protenix JSON, and Chai FASTA using `_row_input_content(backbone, ...)` 
  — so one partner FASTA is consumed by all four backbones per row. Block A 
  followed this pattern (see `scorer/propose.py::_partner_fasta` and 
  `_BACKBONE_EXT`). The build_manifest carries a backbone column so the 
  downstream manifest builder can enumerate (receptor × arm × backbone × seed × sample) 
  rows without re-computing sequence provenance per backbone.

## Integration hook for the Block B manifest builder

The 80 FASTAs need to be exposed to the manifest builder's `_partner_fasta` 
resolver, which currently reads only `docs/EXPERIMENT_CATALOG/sequences/
partners.fasta` (single file). Two options for the follow-up commit that 
wires Block B into `build_block_a_manifest.py`:

1. **Concatenate**: append the 80 FASTAs to `partners.fasta` and reference 
   them by their per-receptor identity slug (e.g. `adrb2_shuffled`, 
   `adrb2_decoy`) from the manifest builder's `CONDITION_PRESETS['block_b']`. 
   Zero change to the resolver.
2. **Multi-source resolver**: teach `scorer/propose.py::_partner_fasta` to fall 
   back on `refs/constructs_block_b/*.fasta` when the identity is not found 
   in `partners.fasta`. Keeps the two spaces separate.

This script does neither — it only produces the FASTAs and the manifest. The 
wire-up commit is intentionally separate so this build step can be reviewed in 
isolation.
